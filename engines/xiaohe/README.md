# 小鹤双拼引擎

螺壳输入法的打字引擎。小鹤按键 → 全拼音节 → **苹果自带的转换引擎（Mecabra）和 RIME（雾凇词库）**出候选，先立刻给出；**本地模型（Qwen3.5-0.8B-Base，在螺壳主控里）结合前文逐词重排**后补发（先快后好）。记住你改选过的词（下次放首位，模型不再改；同一串键改选过几个词时，按改选的次数排；一段里分几次选出来的，比如先翻页选"史"、再选"高"，整串键也记住拼起来的"史高"），在候选窗里按 Shift+⌫ 忘掉一个词（模型选出的整句也不再出现）。记的东西在引擎数据目录的 `memory.json`（`~/.luoke/ime/data/xiaohe/`）：选过的词是原文，忘掉的也存原文，同目录的 `forgotten.json` 列给壳的设置窗口，能撤销；早先的版本只存了"按键 + 词"哈希的那些（`forgotten_hashes`）留着当拦截名单。

光标处原样显示你敲的键（比如 `woxliifj`），不换成全拼：小鹤每两个键一个音节，没有歧义要看；打英文时也不会变成 he liang o 这样的怪串。

也给 emoji 和英文单词：
- emoji 来自苹果，跟在对应的词后面，最多 2 个，例如 xnlm（xiao lian）→ 笑脸 😊 😃。
- 英文单词是拼写跟按键一样的词（不分大小写），由苹果和 RIME 查原始字母得到，最多 2 个。
- 大写字母开头（Shift+字母）就是打英文：候选是拼写一样的英文单词（Github → GitHub、Iphone → iPhone；词典里全小写的词照你的大小写，Hello 不变）和原样的字母，不出中文、不重排；空格选首选，回车原样上屏。
  - 按键拼不成小鹤音节时放第一位（改选过的词仍在最前），例如 github → GitHub、apple → apple Apple。
  - 拼得成时放第二位，例如 hello，而且至少要 4 个字母，所以 go（过）、no（诺）这类常用双拼码不会冒出英文。

博客语料 600 条（首选准确率）：

| | 准确率 |
|---|---|
| 苹果（系统双拼） | 78.8% |
| 本引擎，立刻给出的（苹果 + RIME 合并） | 78.8% |
| **本引擎，模型逐词重排后（门槛 3）** | **约 90%**（macOS 26 上 90.0%，27 上 89.8%；苹果的转换引擎两版略有不同） |

## 速度

打字时每敲一个键，壳问一次。引擎这样赶上空格：

- 先立刻给出苹果 + RIME 的候选，模型逐词选好后再补发。✦ 始终表示模型：还在算时候选条末尾的 ✦ 缓缓呼吸；算完换掉了先给的首选，✦ 就留在新首选后面（它淡入）；没换就消失。
- 敲下一个键时，算到一半的作废。但已经定下、而且定的时候往后看了至少 4 个音节的词，下一次直接沿用。这样最后一个键之后只需要重选末尾几个词。
- 停下 0.3 秒以后再从头选一遍（沿用的词定的时候后面还没打完），结果不同就再补发一次。这一份按空格不会等。
- 模型在 GPU 上算的时候，先把下一步的候选备好；苹果和 RIME 查过的结果一直留着。
- 每步苹果看前 12 个汉字候选、单字最多留 4 个，RIME 取前 8 个汉字候选（emoji 都不算）；每个整句截到最长的首词之后 4 个字（苹果或 RIME 的整句本身被当成首词时，这一步就不截）。模型的用时跟候选数 × 长度成正比。

照壳的用法测，120 ms 一个键：

| | M4（第二步时） | M4 | M5 Max | M5 Max，模型搬进个人化组件后 |
|---|---|---|---|---|
| 最后一个键到补发，中位数 / p90 | 193 / 763 ms | 122 / 186 ms | 57 / 76 ms | 60 / 77 ms |
| 停顿 100 ms 按空格，上屏的首选准确率 | 84.7% | 90.5% | 90.5% | 90.5% |
| 打完立刻按空格，上屏的首选准确率 | 81.5% | 85.5% | 90.5% | 90.5% |

按空格时壳最多再等 150 ms 补发（见设计文档的先快后好规则）。模型搬进个人化组件后每次打分多转两道手，准确率逐条不变，补发慢了约 3 ms。

```bash
./bench.py 语料.tsv                  # 每条问一次：准确率和用时
./bench.py 语料.tsv --typing 120     # 照壳的用法逐键问，算按空格时上屏的是哪一份
./bench.py 语料.tsv --typing 0       # 逐键问，每个键都等引擎答完（结果是确定的）
./bench.py 语料.tsv --typing 120 --score-delay 50   # 每次打分晚 50 ms 交给引擎：在快的机器上模拟慢的（16 GB 测试机（M1）上螺壳每次打分约 66 ms）
./bench.py 语料.tsv --typing 0 --scorer hub --hub <socket> --result 证据.json   # 经主控测，写一份发布用的证据
```

退出码：0 评完了；3 没评成（经主控却一次都没打成分、计时那段里主控拒过打分、引擎一份答复都没给），不写 `--result`，发布脚本据此记"没评成"、不记"没过"；别的非 0 是评测程序或环境本身出错。`--result` 照 luoke-core V1 的证据格式写 JSON（`scripts/evidence.py`）：配件版本和提交号、任务、评测集的文件名和哈希、组合（模型、主控给的任务参数、引擎选项）、机器和芯片、日期、汇总的准确率和用时，以及逐条的对错和用时；不带语料原文。

## 本机统计

模型在真实输入里帮了多少，记在引擎数据目录的 `stats.json`（小鹤是 `~/.luoke/ime/data/xiaohe/stats.json`，全拼在 `quanpin` 下）。只记次数，不记任何文字，不外传。每一段上屏按"选的时候首选是什么"归类：

| 字段 | 意思 |
|---|---|
| `pieces` | 你确认上屏的段数（切走时的自动上屏、按回车原样上屏的字母不算） |
| `star_accepted` / `star_reverted` / `star_other` | 选的时候首选带 ✦：直接用了 / 改选回苹果先给的 / 选了别的 |
| `star_late` / `star_late_model_right` | 模型会换首选，但选的时候 ✦ 还没到；其中你最后选的正是模型那句 |
| `plain_top` / `plain_other` | 首选没带 ✦：用了首选 / 选了别的 |
| `deleted_after_star` / `deleted_after_plain` | 上屏后紧接着退格：这次用了 ✦ / 没用 |

删掉这个文件就从头计。

## 需要的东西

- 苹果的转换引擎：系统自带的私有库。启动时自检，失效就退出并说明原因，螺壳会停用它。
- RIME：librime 由 `scripts/build-librime.sh` 从源码编（部署目标 macOS 14，依赖静态链进一个 librime.1.dylib，lua 插件也合并进去；Homebrew 的只适合本机，装到更老的系统上加载不了），`build.sh` 缺它时会先编；雾凇词库（GPL-3.0）由 `build.sh` 下载到 `vendor/`，不进仓库。第一次启动编译词库约 15 秒，之前只用苹果的候选。
- 模型：在螺壳主控里（`luoke-ime.rerank` 任务）。这个引擎经壳转问[个人化组件](../personal)的 `score`，它再转问主控；开发和评测时个人化组件也能用本机的打分进程（要 oMLX 和 `~/.omlx/models/local/Qwen3.5-0.8B-Base-4bit`），发布版不带。个人化组件没装、模型还没加载好时不重排，其余照常；每隔几秒再试一次能不能打分。
- 所需权限：没有（不联网，所以能转问个人化组件；`"asks": ["personal"]`）。读前文最多 120 字。

## 选项（engine.json 的 options）

`rerank`（用模型重排，默认开）、`rime`（并入 RIME 候选，默认开）、`gate`（模型要比苹果首选高出多少才改，默认 3）、`budget`（每一步给模型多少候选、一次重排最多几步：`auto` 默认，主控按实测给重排标了 slow 时用 `small`；`full` 苹果 12 个、单字最多 4 个、RIME 8 个，步数不限；`small` 6 / 2 / 4，最多 2 步）、`rounds`（单独改最多几步，评测用；0 是不限）。模型目录在个人化组件的选项里。

慢的机器：M1 这类机器上一次打分 p90 一百多毫秒，逐词重排几步加起来三四百毫秒，按空格时壳最多等 150 ms，多半等不到。主控实测出来会给 rerank 标 slow（按实测分，不按内存档位，16 GB 里也有快的机器），个人化组件随打分答复带给引擎，引擎就每一步少给模型一半候选。M5 Max 上实测（博客语料 600 条，`--engine-option budget=…`）：减半后首选 89.8% → 88.8%，最后一个键到选好 p50 42 → 30 ms、p90 70 → 55 ms，每次重排里模型的用时 p90 80 → 55 ms。16 GB 测试机（M1）上经螺壳实测（luoke-core `docs/experiments/coexistence-e2e.md` §5，逐键 120 ms）：首选同样 89.8% → 88.8%，最后一个键到选好 p50 / p90 364 / 539 → 260 / 364 ms；停顿 200 ms 后按空格，不必再等的 46.7% → 85.0%、上屏的首选 82.0% → 87.0%；不停顿就按空格 5.5% → 17.8%、70.5% → 80.3%。每次打分里固定的部分占大头，再减候选收益很小；要赶上 150 ms 得减少最后一个键之后接连的几轮。

所以 `small` 还限步数：一次重排最多 2 步，第 2 步把整句（首词接上苹果或 RIME 对剩下按键的补全）一起定，不再逐词往下选；用户停下 0.3 秒后再不限步数从头选一遍，不同就补发。另外，模型算着的时候来了新键，先把它快的那份候选答了，不等这一步算完（所有机器都这样）。在 M5 Max 上模拟这台 M1 测试机（`--typing 120 --score-delay 50`，每次打分约 66 ms，和这台测试机上螺壳的用时相当；不限步数时模拟和这台测试机的实测对得上：不停顿按空格的上屏首选 80.5% 对 80.3%）：

| `small` 再加 | 最后一个键到第一份答复 p50 / p90 | 到选好 p50 / p90 | 按空格前停顿 0 / 100 / 200 ms 时上屏的首选 |
|---|---|---|---|
| 不限步数 | 34 / 71 ms | 232 / 343 ms | 80.5% / 84.5% / 88.2% |
| 最多 3 步 | 36 / 75 ms | 231 / 290 ms | 80.3% / 83.7% / 89.0% |
| **最多 2 步** | 35 / 74 ms | 177 / 222 ms | 80.3% / 88.2% / 88.2% |
| 最多 1 步 | 16 / 22 ms | 92 / 107 ms | 87.0% / 87.0% / 87.0% |
| **最多 2 步 + 先答新键（现在）** | **15 / 21 ms** | **168 / 204 ms** | **80.7% / 88.2% / 88.2%** |

16 GB 测试机（M1）上经螺壳实测（luoke-core `docs/experiments/coexistence-e2e.md` §6，都是 `small`，逐键 120 ms）：

| `small` 再加 | 第一份答复 p90 | 到选好 p50 / p90 | 停顿 0 / 100 / 200 ms 时上屏的首选 |
|---|---|---|---|
| 不限步数（改之前） | 104 ms | 260 / 364 ms | 80.3% / 82.5% / 87.0% |
| 不限步数 + 先答新键 | 32 ms | 187 / 270 ms | 81.7% / 87.5% / 89.0% |
| **最多 2 步 + 先答新键（现在）** | **32 ms** | **150 / 183 ms** | **83.5% / 88.0% / 88.2%** |
| 最多 1 步 + 先答新键 | 35 ms | 105 / 136 ms | 86.8% / 87.0% / 87.0% |

最多 1 步时打完立刻按空格也赶得上，但停顿 100 ms 以上（平常打字按空格前的间隔就有这么长）比 2 步低 1 个百分点左右；2 步在 M1 上选好的 p50 正好 150 ms。引擎总来得及时（`--typing 0`），2 步让不标 more 的首选 88.8% → 88.2%，停下来后那一遍又回到 88.8%。

停顿后才重排（选项 `pause`，毫秒，默认 0 = 不等；`pause_when`：`slow` 只在主控标了 slow 的机器上，或 `always`）：快打时中间的键不占模型，只在键后停顿这么久没有新键时才重排（luokelabs/luoke-ime#10，评测用，默认关）。16 GB 测试机（M1）上经螺壳实测（600 条，逐键 120 ms，`small`，底座未加载）：

| | 主控打分次数 | 到选好 p50 / p90 | 停顿 0 / 100 / 200 ms 时上屏的首选 |
|---|---|---|---|
| **逐键重排（现在）** | 9571 | 187 / 226 ms | 80.3% / 87.5% / 88.2% |
| 停顿 150 ms 才重排 | 2929 | 447 / 537 ms | 78.8% / 78.8% / 80.2% |

打分请求少了七成，但按空格时几乎都等不到重排，上屏的首选掉回苹果单独的 78.8%：逐键重排时前面几个键已经把词定下了，最后一个键只要接着算；停下来才算就得从头算整句，还要先等那 150 ms。最终首选两者一样（88.8%）。所以不开（主控那边打字时 60 秒不接后台，一段连续打字最多打断一次后台，见 issue）。这次的"现在"一行比上表 §6 慢一些（同一台机器、不同的一天）。

`bench.py` 测的时候像壳一样起一个个人化组件（`--personal`，默认 `../personal`），把转问转给它；不给它记忆的路径，什么都不写进记忆。

```bash
./build.sh                       # 编译、下载词库、自检；RIME_ICE=<已有词库> 可免下载
luoke-ime check .
luoke-ime try . --context "他在婚礼上许下了" --keys '{wait:15000}uiyj{wait:500}{space}'
```

随 LuokeIME.app 发布（`scripts/bundle-engines.sh` 组装：程序、rime_helper、雾凇词库，以及 librime 和它用到的动态库，放在 `lib/`）；在输入法菜单里选「小鹤双拼」。开发时把这个文件夹复制到 `~/.luoke/ime/engines/xiaohe`，会盖过包里的那份（用完挪走）。

[自然码双拼](../ziranma)和[全拼](../quanpin)引擎用的也是这里的代码，只是按键方案不同（`--scheme ziranma`、`--scheme quanpin`）。自然码和小鹤只差韵母的键位表（`Ziranma.swift`、`Xiaohe.swift`）；双拼和全拼的差别在 `Scheme.swift`：一串按键怎么切成音节、每个候选用掉几个键、光标处怎么显示。
